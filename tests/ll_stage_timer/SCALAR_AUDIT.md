# 动态接收分支 Scalar 审查（2026-10-20）

审查基线为 `2c27af8`，范围为组内初发、计数和动态接收的生产源码。
以下成本由源码推导，尚无目标机指令统计或性能结论。

## 按特性交付

首个优化：在 `SendWithDedup` 中用 Scalar 局部变量累计 source mask，
处理完该 token 的 FIRST_HOP 后单次写入 UB。设首跳组数为 F，
原来每 token 对 sourceMasks 执行 F 次读取和 F+1 次写入，
现在为 0 次读取和 1 次写入；F=0 时写入次数相同。
SendPacket 不读取 sourceMasks，最终 GM 发布仍在发送流程结束后，
因此延后这次 UB 写入不改变发布顺序、路由位或发送顺序。
仅修改发送器和对应源码指纹；相关 CPU 回归 53 passed、12 skipped
（缺少 C++ 编译器），尚无 CANN 编译或设备性能验证。
后续候选各用独立提交交付，不与本特性合并。

第二个优化：Sender 使用现有 qSub 直方图和 qWork 表，一次稳定扫描生成
远端路由的 q，包含 FIRST_HOP 尾部所需的 q。保留首 token 的 q=0 约定。
与跨核共享计数 q 的候选相比，此实现不新增 GM 空间、发布协议或全核等待；
每个发送核仍独立扫描。专家数大于 B×K 时直方图放不进现有保守容量，
沿用原前缀路径。非去重模式先完成向量筛选，再复用 qWork；量化仅使用
qDst，不覆盖 q 表。分配和 Host 预算不变。新增路由/分片等价模型，
实际 Scalar 指令数和性能待目标机测量，不能将一次扫描的 Scalar 更新成本忽略。

第三个优化：DIRECT 任务按组建立稳定链表，复用 `serverState_` 作桶头；
去重模式将记录的 token/k 合成展平索引，空出的 word 存 next。逆序建链，
发送仍保持原组轮转及组内 token/k 顺序。非去重的原大组排序路径使用
紧凑索引后面的 next 数组，小组路径保留原一次扫描。next 容量包含在
Host 原有每核 ceil(B/S)×K×16B 预算中，不增加 Host 最大预算或全局协议。
分桶建立本身有 Scalar 成本，小任务不保证提速；复杂度从 O(G×D) 降到 O(G+D)。

第四个优化：复用现有 16 行位置 tile 作单项缓存。连续访问同一批次时跳过
位置表 DMA 及相应 S→MTE2/MTE2→S 依赖；仍每次重新探测 packet flags，
不会缓存“未就绪”结果。每次 Process 的 Init 清空缓存，不能跨窗口/轮次复用。
没有增加 UB、Host 预算或队列协议。收益主要在单批队列及跳过已完成批次后
重复访问剩余批次；多批无重复访问时只有缓存比较开销，不承诺普遍提速。

第五个优化：游标仍每 8 批领取一次，done 查询独立改为每 32 次候选迭代一次。
进入接收时仍检查 done，最后一个完成认领的核仍立即本地退出，CAS/完成计数
语义不变。即使每个候选都被 seen 跳过，也计入 32 次，避免退出检查饥饿。
稳定轮询中这两类共享原子从约 2/8 次/候选降到 1/8+1/32，
不含 CAS、入场和完成更新；其他核发现全部认领后的额外迭代最多 31 次，
这是操作次数界限而非时间界限，需关注目标机尾延迟。

第六个优化：`Classify` 显式外提 token 起点、本组编号和组专家数，
用一次除法求目标组；`BuildReceivePositions` 将逐 record 的 source/expert
除余改为分片起点一次解码和递增回绕，保留原 rotated source 的槽位顺序。
不合并小区间的 DMA，不改发布依赖。编译器可能已做部分不变量提升，
实际指令收益需检查目标汇编。

## 编译错误

`dispatch_server_dedup_counts.h` 的两个 `GM_ADDR` 成员原先逗号连写。
目标编译日志指出第二个成员非法带地址空间限定；已拆成两个独立声明。
`GM_ADDR` 在本地无 CANN 的兼容路径中是 `using GM_ADDR = uint8_t*`，
该路径无法暴露目标环境的宏声明问题。普通 CPU 检查不能替代 CANN 编译。

对整个 `csrc` 的 `GM_ADDR`、`__gm__`、`__ubuf__` 声明进行了候选扫描，
并检查 LL dispatch/combine 成员及新增队列的 `Pointer` 类型别名。
未发现其他同类逗号多变量声明。函数参数各自声明类型，不属于此错误。
本地相关回归 95 passed、23 skipped；跳过项需要 C++ 编译器。
本机无 CANN，不能据此宣布整个分支设备编译通过。

## 优先优化候选

| 优先级 | 位置和当前成本 | 候选方案及约束 |
|---|---|---|
| 1 | Sender 的 `CalTokenSendExpertCnt` 对每条远端发送路由重新扫描其前缀，发起多条向量指令及 V→S 等待 | 参照本组任务，在统计阶段生成远端 q 表，Sender 直接读取。统计按专家分工、发送按 token 分工，必须设计共享位置、发布与存储预算；不能直接复用 R 核私有 UB。收益属于减少指令下发和同步，不能全称为 Scalar 算术收益。 |
| 2 | `SendWithDedup` 的 DIRECT 阶段每个目标组遍历完整任务表，成本约为组数 × DIRECT 任务数；大容量非去重路径也按组反复筛选 | 构造稳定分桶索引/偏移，使发送只遍历对应组的区间。保留组轮转顺序和组内原任务顺序，评估分桶建立成本及额外 UB；不按 EP16 或示例 shape 特化。 |
| 3 | Receiver 每次未命中仍加载 16 行位置表、发起各包 flag DMA、逐项读取归约结果 | 可缓存最近批次的位置表，或缓存已知认领位以跳过部分批次的无效探测。位置表在一次 dispatch 内不变，但缓存须计入 Host UB 预算；跳过行必须避免旧归约值混入 readyMask。只在有重复访问时获益。 |
| 4 | `Next` 大约每 8 次候选批次迭代做一次共享游标 fetch-add、一次 done fetch-add(0)；认领每个非空就绪快照最多两次 CAS，每批完全认领另加一次 done 更新 | 将完成查询周期与 8 批领取粒度分开，或按是否取得进展调整查询频率。必须保留退出检查、空队列处理、游标回绕正确性和公平覆盖；更少原子可能增加尾部轮询。不得领取未就绪行后阻塞等待。 |

当前“每 8 次”包含已在本核 seen 位图中的跳过批次，因此是候选批次迭代，
不等于实际探测包数。CAS 按每次观察到的就绪子集发生，部分就绪和竞争时
一个批次可发生多次 CAS，不能宣传为“每 16 个 token 固定一次原子”。

## 较小的优化与边界

- `Classify` 可显式预计算本组编号、每组专家数和 token 路由起点；
  Sender 的 `sourceMasks_` 单次写回已按上面的独立特性交付。
  编译器可能已做循环不变量提升，应先看目标汇编再判断收益。
- `BuildReceivePositions` 逐 count record 计算 source/expert/slot，并在每个
  非空区间执行向量索引生成和 DMA 同步。可用递增索引替代循环中的除余，
  或合并小区间后批量发布；但这是一次性前缀阶段，不宜优先于反复轮询。
- 本组 `BuildLocalTasks` 已在稳定直方图更新时生成 q，避免了逐路由前缀归约。
  histogram 的读改写存在同专家依赖，不能用普通向量 scatter 直接替换。
- 接收端的清 flag 顺序、lane 退休和 prefix-ready 发布属于正确性依赖，
  不能为了减少 Scalar 下发删除。性能对比应使用 timer OFF，并另用诊断采样定位。

建议先分别测远端 q 生成和 DIRECT 分桶，再测队列查询周期；不要将三类改动
同时合入后仅凭总时延归因。所有候选仍需全 rank 正确性与目标设备性能验收。
