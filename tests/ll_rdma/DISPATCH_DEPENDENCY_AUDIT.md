# Dispatch数学依赖、方案依赖与编码时序审计

本表按用户第二项要求只作审计，不实施候选变更。此次唯一主动修改的dispatch行为是
第一项明确要求的GM stage容量批处理及其必要peer记录修正。此前count源隔离保持。

| 当前顺序/等待 | 是否数学必需 | 判断与后续方向（本次不改） |
|---|---|---|
| 本核完整SendCnt结束后才进入Sender | payload发送不消费本端count发送结果，非固有顺序 | 阶段串行及scratch复用的方案选择；可分离计数职责/存储后重叠。不能仅删数据生产所需的MTE/V依赖 |
| 全count快照→跨核cumsum→完整prefix ready→任务构建 | 每条最终输出依赖其所需前缀，但不天然依赖所有后续条目 | 当前按全局输出行数均分R核任务，需要总数；这是任务划分方案引入的全表依赖。流式prefix或静态专家/source分片需重设所有权 |
| FIRST_HOP全部优先，随后DIRECT | DIRECT不消费FIRST_HOP完成状态 | 调度方案，用于尽早启动relay；可交错但需测网络与接收关键路径，不是正确性bug |
| 准备下一包后才SubmitPending上一包 | 前一包提交不需要下一包内容 | 编码时序为隐藏MTE3暂存等待而推迟提交；可能延后首包。可研究在下一包输入/V操作进行时提交，而不是等待下一包完全准备 |
| 固定8包后quiet | 无数学依据，也不是SDK的8包上限 | 编码中的保守批大小。此次按第一项改为完整GM容量，并修复按包序号位图不适于大批次的问题 |
| 输出lane重用前MTE3_V | 同一存储不能在消费者完成前覆写；不是不同包的数学先后 | 有限UB池的生命周期方案，可通过更细资源分区重叠；现有lane/事件不得直接取消保护 |
| count阶段PIPE_ALL后Receiver重置TPipe | prefix结果与未退休DMA必须可见；全pipeline drain并非数学最小集合 | 共享arena/Reset方案产生的强同步。可研究拆分arena或精确等待，但必须核查每个仍被MTE读取的源 |
| 逐专家V_S后Scalar写count | count字段必须由正确统计产生；逐专家等待不是唯一实现 | 编码策略。已有可选硬件直方图一次显式V_S对照，本次不再调整统计实现 |
| 每包按原路由前缀重新计算q | q值依赖原路由次序，但“重新计算”不是数学依赖 | 计算策略成本，不应误算为网络依赖；当前按既有要求保留逐次Vector q，不自动恢复缓存 |
| 接收跨机包检查全部块FLAG | 正确SO尾可证明前序数据到达，不要求逐块确认 | 当前保守协议校验，且用户此前明确保留完整flag检查；机内MTE不能套用RoCE SO，本次不改 |
| 本核末尾count CQ退休 | SDK队列/源生命周期，非count→payload数学依赖 | 已隔离count源并与同peer/QP的payload quiet合并；跨调用/销毁时再放宽回收边界需另证生命周期 |

真正需要保留的语义边包括：输入数据产生后才能被使用；count就绪后才能计算所需prefix；
packet发布就绪后才能消费对应body；输出数据落位后才能供后续算子读取。
具体的SetFlag/WaitFlag、PIPE_ALL、某个阶段划分只是实现这些语义的手段，不应反过来当作数学约束。

结论：主要是方案选择和保守时序造成的优化空间，不能把所有等待称为编码错误。
已确认的编码限制是8包常量；直接扩容而不改firstPeers_则会产生位宽问题，此次已同时处理。
尚未用设备测量证明其他候选的收益，也没有删除这些候选对应的同步代码。
