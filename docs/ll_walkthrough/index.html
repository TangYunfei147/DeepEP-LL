1. 两个算子究竟解决什么问题？

在MoE里，每个token是一行长度为H的向量。路由器为它选择K个专家，并给出K个权重。专家分布在不同rank上，因此“知道该算什么”之后，还要解决“数据如何到达专家、结果如何回到源token”。

y[s,t] ≈ Σₖ w[s,t,k] · Fexpert[s,t,k](x[s,t])

dispatch负责重排和传输输入；combine负责把专家结果按原token归并。专家网络Fₑ由调用者在两者之间执行。它既不是dispatch中的某个循环，也不是combine帮你补做的计算。

为什么

源卡上的token顺序，与目的卡上按专家执行的顺序不同。

做什么

dispatch展开路由，把每条专家任务放到正确的目的卡和输出行。

得到什么

专家可按本地专家连续处理自己的行。

为什么

一个源token会产生多份专家结果；调用者最终只需要一行。

做什么

combine使用dispatch留下的路由记录回传、乘权重并求和。

得到什么

输出重新按源rank原token编号排列。

“≈”是有意写的

数学目标是加权和；FP8传输、BF16/FP16转换，以及M4先形成partial再由M5求和，可能带来舍入差异。文中小数例子刻意使用可精确表示的数，不把它当作真实精度或性能测量。

2. 先分清这些名字

名字本篇含义不要混淆
rank / 卡EP通信域中的一个参与者；本项目按每主机16个连续rank划分物理机界。rank不是AIV核，也不是专家。
AIV核 / core一张卡内并行执行这段通信kernel的核。56核是本文例子，实际C来自设备查询。
expert / 专家一个逻辑计算模块。E384、EP32时，每卡12个专家。expert205在rank17，不是rank205。
B / H / K / E / P本rank实际token数 / 向量宽度 / 每token路由数 / 全局专家数 / EP规模。本文主例B2、H3584、K4、E384、P32。
B_capnum_max_tokens_per_rank，Host容量参数；主例256。不是实际B，也不是元数据核数。
M / S / Rdispatch元数据核数 / payload发送核数 / 接收核数。C56、M4时S=R=26。combine并不沿用这个4+26+26拆分。
G / group逻辑去重组大小。当前P≤16用G4，P>16用G16。G4不代表一台机器只有4张卡。
k / firstK某条路由在token的top-k列表中的位置，取值0…K-1。包头字段topK存的是这个位置，不是shape里的K。
q同一源rank发往某个expert的第几条路由，从0开始。不是包到达次序，也不是输出行号。
slot / 固定槽通信GM中预先可计算的稀疏收件地址编号。它无需prefix，却可能有很多空洞。
row / 输出行dispatch最终展开输出中的紧凑行号。它依赖count/prefix；combine按同一行读取专家结果。
count / prefix每个expert/source的条数 / 按固定逻辑顺序的累计和。计数对象是完整专家路由，不是去重后的跨机包数。
DIRECT / FIRST_HOP / TERMINAL专家任务在通信协议中的角色，数值为1 / 2 / 3。不是flag里的1.0 / 1.5 / 1.25。
GM / UB / lane全局内存 / 核内暂存 / 一份循环复用的暂存槽。lane不是另一张卡，也不等于GM批容量。
MTE2 / MTE3常见方向是GM→UB / UB→GM的数据搬运流水。操作会异步进行，代码走到下一行不代表搬完。
Scalar / Vector标量控制、地址计算 / 向量计算、打包、归约。事件名里的S是Scalar，不是业务上的S发送核。
QP / WQE / CQ传输队列 / 提交的工作请求 / 完成队列。路由序号q与QP完全不同；quiet用于退休在途请求。

3. 一组贯穿三篇的具体数据

只展开源rank0的两个token，其他31个rank仍存在。为了让所画专家的count可手算，可让其他源rank选择expert4/5/6/7；这些合法路由会影响rank0的其他专家，不影响下表高亮专家。我们只展示向量的前两个分量，实际H仍为3584。

源tokenk0：本组DIRECTk1：异组首跳k2：异组成员k3：异组成员
t0e0 → rank0；w=¼e192 → rank16；w=¼e205 → rank17；w=¼e218 → rank18；w=¼
t1e1 → rank0；w=½e192 → rank16；w=¼e229 → rank19；w=⅛e242 → rank20；w=⅛

专家位置由L=E/P=12计算：expert205的目标rank为205//12=17，本地专家号为205%12=1。每个token都选了三个主机B上的专家。它们先合成一份FIRST_HOP发到rank16，再在主机B内展开。rank16既是一个真实专家所在卡，也是这次转发与partial归并的承担者。

为什么两个token的首跳都选k1？

当前G16+RDMA实现会看该目标主机内四个连续4-rank小组，优先选包含最多专家路由的组，再选其中最小原始k；按路由条数统计，不按不同卡数。t0的rank16/17/18都在同一小组；t1的rank16/19有两条、rank20所在小组只有一条。因此两者都选k1。首跳并非总是固定rank16。

减少了什么，没有减少什么

只看t0的跨机payload：三份输入跨机发送变成一份FIRST_HOP；返回时三份结果变成一份partial。三个远端专家仍各执行一次。count控制消息也仍按完整路由统计；不能把“payload少了两份”说成所有通信都只剩一个包。

5. Host把什么交给设备？

为什么

设备kernel需要确定尺寸、地址、格式和路由，而Python张量与会话对象不能直接当协议。

做什么

Python分配输出和handle，Host检查形状/类型/容量，上传CommArgs与tiling，选择编译特化。

得到什么

一次dispatch kernel启动，以及返回给调用者的展开数据、handle与事件。

# 教学伪代码：返回值和参数名做了简化
recv_x, handle = dispatch(x, expert_ids, original_weights)
expert_y = run_local_experts(recv_x)     # 调用者负责；保持展开行的对应关系
y = combine(expert_y, handle)           # 专家输出尚未乘router权重

CommArgs回答“我是谁、可访问哪些peer、对称GM和RDMA暂存在哪”；tiling回答“B/H/K/E、格式、容量和G是多少”。这里的tiling不是另一份路由表。Host还固定本通信器实际核数，避免跨调用布局和QP身份发生变化。

handle字段主要在哪里产生combine为什么需要
token_typeR核搬出每行时区分DIRECT、FIRST_HOP、TERMINAL。
destination_indexR核搬出时DIRECT/FIRST_HOP保存源rank、源token、return-k；TERMINAL保存固定slot。
relay_read_indexFIRST_HOP搬出时保留成员expert/q、自己及成员的原权重，供M4读取并加权。
source_mask源S核分类后源卡知道哪些k真的会收到DIRECT或partial。
source_weights源S核DIRECT保留原权重，FIRST_HOP返回槽权重改为1。
send_counts元数据核完成prefix名字容易误导：此处存目的卡的累计接收前缀；末项是有效展开行数T。
不要提前做两次加权

当前LL combine读取handle里的权重；输入应是未乘router权重的BF16/FP16专家结果。公共LL路径不接受再传一份topk_weights或bias来覆盖它。

同步与容量的第一遍解释

Python用专用通信stream和事件建立输入生产、kernel、后续消费的先后关系，并保留张量生命周期。事件wait建立stream依赖，不等于Python线程已经等到NPU执行完成。输出可能按上界预分配；真正有效行数由设备prefix给出。不要把分配容量当有效token数。do_cpu_sync会影响Host能否提前得到精确行数和返回张量范围，但不替代设备count协议。

6. 只先记住三种“地址”

看代码时最容易迷路的是：同一个token先后出现于多个缓冲。它们不是同一个编号空间。

位置如何编号主要作用
通信收件槽source、destination、localExpert、q → slot发送方不等prefix，也能确定写入位置。
dispatch展开输出 / 专家结果prefix → row让专家输入连续，并用handle把这行结果关联回原路由。
combine返回槽source-token × K + return-k源卡按source_mask等待有效返回槽，再合成一行y。

t0在rank16的收件slot是384，但搬到展开输出的row0；combine partial最终回到rank0的return槽1。384、0、1都描述同一条首跳任务的不同阶段，不能互相替换。

内存分层

每rank对称工作区固定8GiB，分成两个4GiB bank；每次dispatch或combine launch轮转一次bank。RDMA发送另外使用每物理核128KiB的注册GM暂存。UB负责核内计算/打包；NIC读的是注册GM源，不能直接把一个UB地址当RoCE源。
