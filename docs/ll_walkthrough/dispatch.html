Dispatch：先有可写地址，再有输出行号

M核准备“收多少、放哪行”，S核发送输入，R核把固定槽中的数据转成专家可用的连续行。

1. Dispatch的交付物：输入展开数据＋回程地图

为什么

每条专家路由都要有一行输入，但源端不知道最终紧凑行号。

做什么

把数据送到可预先计算的通信槽，再按count前缀搬到输出；同时生成combine要用的handle表。

得到什么

目的卡上的有效输入行按本地expert、源rank、q排列；源卡保存回包mask和权重。

正文以去重路径为主。当前P>16始终去重；P=16时，B_cap>32才去重。不要沿用旧文档的“EP32/B32关闭去重”条件。去重只合并源端发往同一个异组的重复payload，不减少原始专家路由数量。

2. 入口先确定“本轮在哪、我做什么”

Host先验证形状、格式、工作区与核数，再进入对应编译特化。Device读取tiling；所有核各自轮转magic，得到本轮bank。每个核有独立512B状态槽，空任务核也必须轮转，不能把它改成少数核才执行。

角色C56/M4时的物理核随后的主要工作
metadata0～3SendCnt、RecvCnt、prefix、任务表、通知；末尾退休count的CQ。
S4～29按源token分片，直接开始payload工作。S逻辑编号=物理核号−M。
R30～55先扫描固定槽；取得prefix后再按均分输出区间搬出。R逻辑编号=物理核号−30。
CTRL[60]为什么也出现在这里？

部分q/count归约把整数位模式作为FP32次正规数处理，需要保留其低位。外层kernel保存并调整数值控制，结束后恢复。S虽然不再执行SendCnt，也仍要计算q，所以不能把这项设置只留给metadata核。第一遍串讲只需知道它保护数值语义，不是通信屏障。

3. M核：先告诉每张目标卡“你会收到多少”

为什么

目的卡要知道每个expert/source组合的有效数量，才能判断空槽、分配输出行并决定何时完成。

做什么

每个metadata核读取完整B×K路由，按目标rank轮转统计该卡全部专家，再发布count。

得到什么

每张目的卡得到所有源rank对其各本地专家的计数；0也是必须发布的合法结果。

本机目标与跨机目标分别轮转。M=4时，源rank0的核0处理本机0/4/8/12和跨机16/20/24/28；其他核各平移1。不是先分全局专家再取本机交集，也不是把B×K输入切成四小块。

for target in remote_targets[my_meta_core :: M]:
    counts = count_all_routes_for_experts_of(target)
    send_one_remote_count_frame(target, counts, tail_ready=1)

for target in local_targets[my_meta_core :: M]:
    counts = count_all_routes_for_experts_of(target)
    publish_local_fragments(target, counts)   # 原布局的body → commit

# 本机各target拥有独立UB源记录；发送完成前不能覆盖
# Remote count的GM源也与payload stage隔离，SendCnt内不逐帧quiet

如果只盯flag，无法区分“这个槽本轮没有任务”和“包还没到”；count同时解决这个终止条件问题。t0/t1都去expert192，所以源rank0给rank16的localExpert0报count=2。去重使源端只各发一个首跳包，并不改变这两条路由。对rank17的localExpert1报1；没有路由的expert/source组合报0。

控制消息为什么不能套用payload包长？

一个远端rank的count帧是“每专家32B记录＋32B尾commit”，并非480B+32B的payload wire。EP32/E384时每卡12专家，因此远端count消息为12×32+32=416B。本机NDR帧保留原分段地址和独立commit，发布body后用既有MTE3依赖再发commit。物理帧如何分段，不再决定实际发送核；该目标rank的所有片段由同一metadata核发送。

4. M核：把count变成行号，而不是等待payload

目的卡维护逻辑矩阵count[localExpert][sourceRank]。它有(E/P)×P=E条记录。metadata核按这个逻辑顺序分连续片段，轮询自己的记录ready，取出真实count，求片内prefix和片段总数。

# 目的rank d上的逻辑顺序：expert在外，source在内
record_id = local_expert * P + source_rank
count[record_id] = 从该source到该expert的原始路由条数

my_prefix = cumulative_sum(my_count_fragment)
publish(my_fragment_total)
offset = sum(total of earlier metadata fragments)
global_prefix_fragment = my_prefix + offset

# 各核写自己的prefix片段和输出row→slot表，最后发布片段完成通知
为什么两级prefix？

若每个核只做自己的累计和，每段都会从0重新编号，输出行就会重叠。前面各段的总数之和，正是当前段应加的全局偏移。这里等的是其他metadata片段，不是所有payload都到达。

recordcount全局prefix对应输出区间
rank16：expert192 / source022[0,2)
rank16：expert192 / source1…310仍为2空区间
rank16：其余本地专家 / 各source0仍为2空区间

本例meta0持有的片段总数是2，其余片段是0。它们仍都要完成汇合。最后send_counts[E-1]=2；专家192的计数为2，其他本地专家为0。

逻辑顺序不等于物理count地址

NDR多机count按source-major帧存放，本机和跨机的commit落点也不同。CountFrame与BuildCountReadPlan负责地址映射；不能把逻辑record_id直接乘512当成所有后端的实际地址。接收侧先取commit，再读body。共享帧commit在所需读者完成快照后清理，避免一个核提前清掉另一个核还要读的ready。

普通已消费count整32B清零；本机prefix完成标志用正常float1.0，避免跨expert shape时旧整数prefix被误认成新标志。

5. 两套坐标：稀疏slot与紧凑row

发送方只用路由和q就能算slot。目的卡收到count后，才知道每组有效slot应该连续放到哪些row。两者分开，才能让发送与转发早于prefix完成。

local_expert = expert_id % (E/P)
slot = (((source + destination) % P) * (E/P) + local_expert) * B + q

record = local_expert * P + source
row_begin = 0 if record == 0 else prefix[record - 1]
output_row = row_begin + q

packet_address = peer_base + bank_offset + dispatch_offset + slot * packet_bytes

主例在rank16：localExpert=0、source=0、B=2。t0的q=0，slot=384；t1再次去expert192，q=1，slot=385。两者在专家输入里的row分别为0和1。

每卡候选槽总数是E×B=768。rank16本例只有2个槽有效，因此扫候选槽与搬出有效行不能用同一份负载分配。

为什么

转发要在未知prefix时就开始，必须提前知道唯一owner。

做什么

固定转发owner=slot % R；metadata按总有效行数T给R核均分区间。

得到什么

转发不会因发现顺序不同而重复；搬出行数每核最多差1。

# 由metadata0生成R核描述符；其他metadata核已生成row→slot片段
begin[r] = floor(T * r / R)
end[r]   = floor(T * (r + 1) / R)
publish descriptors, then publish each R core's own 32B ready slot
任务转发owner搬出owner
slot384 → row0384 % 26 = R20（物理核50）区间[0,1)属于R12（物理核42）
slot385 → row1385 % 26 = R21（物理核51）区间[1,2)属于R25（物理核55）

每个R核读并清自己的通知，再加载prefix、描述符和自己的row→slot片段。没有搬出行的R20/R21仍须执行转发；“输出任务为0”不是退出条件。

6. S核：先决定需要发送哪几份，再计算q

S按源token连续分片。本例B2、S26，只有逻辑S0/S1有token任务，对应物理核4/5。每个核先扫描自己的token路由，建立DIRECT集合与异组多路由集合。

路由情况选择的角色原因
目标与源在同一逻辑组DIRECT已经是组内访问，不再通过首跳增加一层。
某异组只有一条路由DIRECT没有重复payload可合并。
某异组至少两条路由一个FIRST_HOP，其余变成它的成员先把一份相同输入送进组内，再由首跳卡分发。
for token in my_source_tokens:
    direct, grouped = classify_by_destination_group(routes[token])
    mask = bits(direct)
    for members in grouped:
        first_k = choose_real_expert_as_first_hop(members)
        send(token, first_k, members)   # 每核先发所有FIRST_HOP
        mask |= 1 << first_k
        source_weights[token, first_k] = 1
    remember_direct_tasks(token, direct)
    source_mask[token] = mask

for direct_task in stable_destination_group_order:
    send(direct_task)
    source_weights[token, k] = original_weight[token, k]

q按原始路由顺序计算，不按实际发包顺序。通常可理解为展平路由数组中，当前路由之前出现相同expert的次数；本例同一token不重复expert，符合这段q计算使用的前提；首token的q为0。FIRST_HOP成员也分别携带自己的q。因此即使FIRST_HOP先发、DIRECT后发，目标slot仍固定。

t1DIRECT(k0)＋FIRST_HOP(k1)0011（二进制）k0=½，k1=1；k2/k3不消费
首跳原权重没有丢

首跳原权重和所有成员权重保存在FIRST_HOP包尾，后来由M4使用。源端把返回槽权重改成1，是因为那里将收到“已经加权求和”的partial。

7. 打包与发布：数据就绪和源缓冲可复用是两件事

一次payload先在UB中准备数据、scale和尾部路由，再打包到wire lane。预量化FP8输入直接搬入FP8字节与配套scale；不会再执行内部量化。多个连续发送使用同一token时可复用输入，每个包仍重建自己的header/tail。

逻辑内容主例t0 FIRST_HOP的内容
payload / scalesx[t0]的H个FP8字节；配套scale字节原样传输。
header（32B）srcRank=0，srcTokenId=0，topK=1，type=2。
read-index第0项（8B）成员数N=2；自己的原权重¼。
后续成员项（每项8B）e205/q0/¼，e218/q0/¼；expert与q打包在同一uint32。
每个wire块的flag（32B）通常全1.0；FIRST_HOP首块首float置1.5。之后本机接管会改成1.25。

H3584/K4预量化FP8：数据3584B、scale112B，加对齐header/成员信息后需要8个wire块，整包4096B。BF16 combine只带结果向量和flag，整包7680B。具体地址由布局helper算，不能把图上几个字段的长度直接相加后省掉对齐。

# 同机（含self）
MTE_copy(packet_UB, peer_fixed_slot)

# 跨机：UB不能直接作为NIC发送源
stage_packet_to_registered_GM()
wait_MTE3_to_Scalar()                   # GM源完整后才能post
put_one_WQE(GM_packet, peer_fixed_slot)
# 不逐包quiet；保留GM槽，批满或末尾时对用到的peer逐一quiet

目标RoCE契约：同一WQE尾片具有SO，之前的数据先到达，片内保序。接收端完整flag检查包含最后32B，因此不需要为这条payload再单发一个尾flag。这不提供跨独立WQE或跨QP的全局顺序；count与payload仍各自发布、各自检查。

批处理实际省的是什么？

每核注册GM stage为128KiB：4096B包可容纳32槽，7680B包可容纳17槽。一个包仍对应一次put；满批后对本批出现过的peer各quiet一次。多个peer不等于一次全局quiet，quiet也不表示对端已经消费。

dispatch有一个“已stage、尚未post”的pending包，可与下一包不同UB lane的准备重叠。下一次提交或末尾Flush会先SubmitPending。UB lane数受UB预算限制，不能把32个GM槽误称为32条UB流水lane。SDK可借用提交scratch，GM源必须保留到CQ退休。

8. R核：一个循环推进两套所有权

R核不能先完全做完转发再开始搬出，也不能在一个未接管包上死等。它交替执行三个动作：扫自己的固定候选槽、查询自己的prefix通知、处理自己的搬出/清理任务。

while not prefix_ready or forward_work_left or output_pending:
    for slot in next_fixed_owned_batch():       # owner = slot % R
        if already_seen(slot): continue
        if prefix_ready and q_is_invalid(slot): retire_candidate(slot); continue
        if not all_packet_flags_ready(slot): continue
        remember_seen(slot)
        inspect_header(slot)
        if type == FIRST_HOP:
            copy_full_packet_to_my_UB()
            forward_UB_copies_as_TERMINAL()      # 原GM header不改
        publish_local_marker(slot, 1.25)

    if not prefix_ready: try_acquire_my_notice_and_tasks()

    for task in next_output_batch():
        if not packet_ready(task.slot): continue
        if not task.moved:
            compact_body_to_output_row_and_write_handle()
            task.moved = True
        if packet_marker_is_1_25(task.slot):
            clear_all_packet_flags(task.slot)
            remove_pending(task)

DIRECT与TERMINAL只需读取header做接管；FIRST_HOP才额外读取整包，并从副本向成员发包。成员包标记成TERMINAL，首flag恢复1.0，因此不会在终点再次转发。原GM中的FIRST_HOP身份保留给搬出核和combine。

为什么

输出owner与转发owner可能不同；输出先清flag，会让还没扫描到它的转发owner漏包。

做什么

输入读取和必要转发提交之后，固定owner写1.25；输出owner可先搬出，但清flag必须等这个状态。

得到什么

没有重复转发、没有重复搬出，也不把两个核绑定为一个owner。

接管标记来自独立的lane元数据暂存，不改写转发DMA仍在读的wire副本。转发用的UB由MTE3完成事件保护；输出读完原包后才允许清其flag。1.25不是远端消费ACK，也不是CQ完成。

完整检查究竟检查什么？

dispatch先读取每个32B flag中的8个float，再归约所有块。完整Compact总和为8N，FIRST_HOP为8N+0.5，Taken为8N+0.25；其他状态继续等。不是只看第一个1.5或1.25。搬出始终去掉480/32间隔，首标记只负责发布/接管，不再决定搬出布局。

位图负责“固定槽已经接管”，pending索引高位负责“这一输出row已搬过”。两者对应不同owner，不能合并成一个状态。若输出任务为空，仍要等通知、清自己的通知槽并完成固定转发范围。

9. 结束时留下什么，释放什么？

位置本例t0留下的内容后续用途
rank16展开row0x[t0]；type=FIRST_HOP；destination=[0,0,1]；成员信息含e205/e218及q/weight专家192计算后，M4从同一row读取它自己的结果，并读取成员stage。
rank17展开row0x[t0]；type=TERMINAL；destination=[410,-1,-1]专家205计算后，M1把结果放到固定stage slot410。
rank18展开row0x[t0]；type=TERMINAL；destination=[436,-1,-1]专家218计算后，M1写stage slot436。
源rank0的handlet0的source_mask=0011；active weights=[¼,1]M5只等返回槽0/1，并按正确的权重合成y。

最终输出row顺序按expert/source/q确定，不随网络到达顺序变化。接收R核回收自己的lane并完成清理；S核完成payload批次和source表写出；metadata核完成自己的count CQ退休。每核最后有既有流水收尾，后续计算stream通过事件等待kernel完成后再消费结果；这不是把stream wait当成Host同步完成。

复用的前提必须完整保留

所有rank同一调用顺序、单stream串行、固定核配置、双bank、零计数发布和正确的flag清理共同保护下一轮。没有“看到后续还有通信，所以总安全”的捷径。combine的Host复用协调还会在下一篇单独说明。

检查理解：slot384的包已写入row0，但flag仍为1.5时，R12下一步应做什么？——保留已搬出状态，继续其他任务；不能清flag，也不能原地阻塞整个循环。

第二遍：如何读事件名？
事件或操作要建立的依赖典型原因
MTE2_S / MTE2_V搬入完成后，Scalar / Vector才能消费。包头读取、flag归约、输入向量计算。
V_MTE3Vector写好UB后，MTE3才能读它。发出刚打包的wire。
MTE3_V / MTE3_MTE2旧MTE3不再读UB，Vector / 新MTE2才可覆写。循环复用同一lane。
MTE3_SMTE3完成后，Scalar才能继续相应发布动作。注册GM源完整后post NIC请求。
PIPE_ALL本核相关流水完成。退出或重新解释一片共享UB前的已有收尾。

事件名的S表示Scalar，不是业务S核。SetFlag/WaitFlag管理核内事件；包里的GM ready flag是另一套协议。PIPE_ALL不是跨rank屏障，MTE3_S也不等于NIC的CQ完成。

去读源码时的三个问题
  1. 每次写UB之前，谁可能还在读这块UB？找对应lane事件。
  2. 每次发ready之前，真正的数据写是否已经满足发布依赖？区分MTE和RoCE。
  3. 每次清flag之前，所有需要原GM数据/标记的消费者是否已经完成必要读取？
