Combine：把专家结果合成原token的一行输出

DIRECT直接回源，TERMINAL留在组内stage，FIRST_HOP形成partial；源卡最后只聚合实际会返回的槽。

1. Combine从专家结果开始，不是从原输入开始

专家已经对dispatch展开后的每行执行Fₑ。combine输入是这些未乘router权重的BF16/FP16结果，以及对应dispatch返回的handle。当前公开LL接口不接收原生FP8 combine输入。

为什么

专家行已经按目的卡重排，仅看结果张量无法知道它来自哪个源token。

做什么

用handle中的type、destination、成员表、source_mask和source_weights恢复回程。

得到什么

每个源rank得到按原token顺序排列的[B,H]输出。

行的对应关系不能丢

如果专家计算内部做了排序或分桶，交给combine前必须保持或恢复与dispatch展开行一致的关系。destination_index[row]描述的就是expert_y[row]。不要把一份结果配到另一个handle。

2. 用三种角色理解M1～M5

FIRST_HOP不是一张只做网络转发的空卡：它也有自己的真实专家结果。TERMINAL是由首跳转发得到输入的成员专家，它的结果先留在目的组内，供首跳卡主动读取。

角色主要路径回源位置
DIRECT（type1）M3直接把未加权专家结果发回源卡。原source-token × K + 原k。
TERMINAL（type3）M1把本行结果写到本机固定stage；M4由首跳卡读取。不单独写源卡返回槽。
FIRST_HOP（type2）M4读自己的结果和所有成员stage，按原权重求partial，再回源。source-token × K + firstK。

当前combine仍是前后半核分工：C56时前28核做DIRECT回传，后28核做组内等待、partial和源聚合；最后8核是后半核中的通知子集。dispatch的4+26+26没有被带进combine。图是每核程序顺序：前半核完成自己的M1即可进入M3，不必等全卡M1结束；等全卡M1的是M2通知核。

3. Host先处理跨调用复用，Device再轮转bank

Python检查handle属于当前buffer、包含完整LL payload元数据，且专家结果形状/类型匹配。当前LL只支持默认调度/stream选项，不接受额外权重或bias。它随后把结果与handle各表交给Host launcher。

在启用Host协调的NDR会话中，启动combine前执行combine_reuse协调；准备阶段会按布局需要清理返回flag。dispatch可能改变B/H/K并占用之前的combine区域，所以不能只因为同一个buffer还活着就假定旧返回区永远干净。

# 简化的Host逻辑
check_matching_handle_and_unweighted_expert_output()
if host_coordinated:
    prepare_result_window_flags_if_needed()
    coordinate_previous_call_completion_across_ranks()
launch_combine_on_comm_stream()

# Device每核进入后
bank = rotate_own_magic_once()       # dispatch与combine都轮转
T = load(handle.send_counts[E-1])   # 实际专家结果有效行数
三种“数量”在这里同时出现

B是本卡原始源token数；T是本卡收到的专家输入有效行数；分配容量只是内存上界。M1/M3/M4按T选专家行，M5按B合成源token。即使T=0，B通常仍非零，本卡仍可能需要M5等待自己的回包。

4. M1：把TERMINAL结果放到别人能找到的位置

为什么

首跳卡不知道成员结果的紧凑row，也不能猜别的卡的prefix；它知道的是原来的expert/q。

做什么

所有核筛出type3行，均分这些行，按destination_index里的slot写本机stage。

得到什么

FIRST_HOP可用source、member expert和q重算同一个slot，读到成员结果。

terminal_rows = rows_with_type(TERMINAL)
for row in my_balanced_share(terminal_rows, all_C_cores):
    slot = destination_index[row][0]
    store_stage_with_zero_gaps(stage[slot], expert_y[row])
wait_my_stage_writes_complete()
publish_my_prepare_done_to_each_notifier_row()

rank17的t0在专家结果row0，但Table2里保存slot410；M1把它写入stage_base + 410×stage_stride。rank18对应slot436。这里使用本次combine的bank和stage基址，不是复用旧dispatch那一包的数据。

主例stage_stride为ceil(2H/480)×512=7680B。末段即使不足480B，也把对应32B间隔清零。stage结果是否可读由M2组内通知决定，这些零间隔只用于维护共享GM的布局安全。

为什么不能直接连续写2H字节？

新的dispatch会在prefix前扫描固定候选槽。工作区随B/H/K或算子切换可能重叠；若combine把任意原始结果写进未来flag的位置，旧浮点数据可能看起来像ready。保持统一512B周期末32B为零，避免这类跨case误认。零来源复用本阶段未使用的result UB，不额外增加一套活跃payload缓冲。

5. M2：先证明本卡写完，再证明本组都写完

M4会从同组其他卡的stage读取数据。当前kernel无法仅凭本核M1完成，就推断其他核或其他卡也完成了。通知协议分成两层：

  1. 卡内prepare done：每个核完成自己的M1写入后，给8个通知核各自的done行发布一个标志。通知核等待本卡全部C个核，不会互相清掉对方尚未读取的行。
  2. 组内server ready：最后8个核分担G张卡的通知。每个目标R核有自己的ready行，收集本组G张卡的标志。该R核取得完整行后清自己的行，才能进入M4。
# 仅最后8个通知核执行
wait(all_C_prepare_done_in_my_row)
clear_my_prepare_row()
for peer in my_group_notification_targets():
    publish_ready_to_each_receiver_row(peer)

# 所有后半核执行
wait(all_G_cards_ready_in_my_receiver_row)
clear_my_receiver_ready_row()

主例G16的所有peer都在同一台机器，通知走MTE；G4时只等本逻辑4-rank组。它不是32rank全局屏障，也不是“8张通知卡”。前半核M3无需等待组内ready，可以独立回传DIRECT。

空任务核也必须发布done

“我没有TERMINAL”意味着我这份M1工作已经完成，而不是可以不参加通知。否则通知核会永远等不到这一份。

6. M3：DIRECT原样回源，留到M5再乘权重

前半核筛选type1行，保留原row及其源rank信息；按源逻辑组遍历，稳定轮转分配DIRECT任务。每个核只读自己的行与路由三元组，使用lane搬入结果、打包、发回。

for row in my_direct_rows:
    source, token, return_k = destination_index[row]
    value = expert_y[row]                  # 此处不乘router权重
    packet = pack_480_data_32_flag(value)
    destination = result_base[source] + (token*K + return_k)*packet_bytes
    send_return_packet(destination, packet)
submit_final_pending_packet()

t0的expert0结果[4,8]写回源rank0的返回槽0。因为目的就是本卡，这条走本机MTE；其他DIRECT若来自另一主机，会用RoCE。DIRECT描述算法角色，不保证物理距离是本机。

为什么回传批处理不等于把多个token合成一个put？

返回槽按token×K+k分散排列，中间可能属于别的producer。当前每个结果仍是一包、一次put，只是在128KiB GM暂存中保留多个在途包，按peer合并quiet。H3584时每包7680B，可放17包；17个包同peer时批尾可只quiet一次，peer不同则逐peer退休。

combine调用SendReturnPacket时使用立即提交路径，不等待下一个token的归约才post本包；M3最后提交pending并回收自己的输入/输出lane，尾批注册GM仍由外层kernel持有。

7. M4：FIRST_HOP读取成员并形成partial

为什么

若每个成员都单独跨机返回，dispatch节省的重复跨机流量会在回程重新出现。

做什么

首跳卡把自己的结果与TERMINAL成员结果按原权重求和，形成一个组内partial。

得到什么

每个FIRST_HOP只向原source-token的firstK槽返回一个结果。

后半核筛出type2行，再按源逻辑组和稳定轮转任务分工处理。它从destination_index取得source/token/firstK，从relay_read_index取得N个成员及N+1个权重。

for first_hop_row in my_owned_type2_rows:
    source, token, first_k = destination_index[first_hop_row]
    members, weights = relay_read_index[first_hop_row]
    values = [expert_y[first_hop_row]]       # 自己的专家结果
    for member in members:
        peer, local_expert = split_expert_id(member.expert)
        slot = (((source+peer)%P)*local_experts + local_expert)*B + member.q
        values.append(read_local_peer_stage(peer, slot))
    partial_fp32 = weighted_sum_in_member_order(values, original_weights)
    partial_low = round_to_BF16_or_FP16(partial_fp32)
    send_to_source(token, first_k, partial_low)
submit_all_remaining_puts_before_entering_M5()

t0的M4在rank16读取本卡row0=[8,4]，再主动读取rank17的stage410=[12,0]、rank18的stage436=[16,12]。这些成员与首跳必须处于同一G组，因此这里是同机peer MTE读取，不是跨机RoCE get。

代码先按顺序Cast成FP32，再逐项乘权重并累加，最后Cast回BF16/FP16打包。成员次序是自己在前、包尾成员在后。改变这个顺序或去掉中间Cast，不能仅凭代数等价认定逐bit结果不变。

为什么必须先post完M4，才能进入M5？

M5会等别的卡返回。如果各卡都把最后一包留在本地“尚未post”状态，再一起等待回包，就可能互相等住。因此M4结束时显式SubmitPending。但它不必等尾批CQ后才进入M5：消息已提交、注册GM源仍保留，NIC可以继续进展。

8. M5：在源卡按mask等待，再恢复一行y

后半核此时转而处理本卡的源token，按B连续分片。source_mask说明哪些返回槽实际有producer；等待一个被合并掉的k2或k3，会永远等不到包。

t00、1[4,8]、partial[9,4]¼、1[10,6]
t14、5[2,6]、partial[4,5]½、1[5,8]
for token in my_source_tokens_in_ready_order:
    active_k = bits_set(source_mask[token])
    wait_until_returns_ready(token, active_k)
    y_fp32 = 0
    for k in increasing_original_k(active_k):
        returned = read_return_slot(token*K+k)
        y_fp32 += float32(returned) * source_weights[token,k]
    y[token] = round_to_output_dtype(y_fp32)

t0：M4已经算出¼[8,4]+¼[12,0]+¼[16,12]=[9,4]。M5再加DIRECT的¼[4,8]=[1,2]，得到[10,6]。如果把partial再乘首跳原权重¼，远端三个专家都会被重复缩放。

C56/B2时，combine的28个后半核按源token分片：t0由源rank0的物理核28聚合，t1由物理核29聚合。这与dispatch阶段rank16上负责搬出的物理核42/55完全不同；handle保存的是数据身份，不要求跨算子沿用同一个核。

就绪检查与dispatch有何不同？

M5读取这个token全部K个返回槽的每个32B flag块，归约各块首float，覆盖每包的最后块；期望值为popcount(source_mask)×blocks。主例K4、blocks15、mask0011，读取60个flag块，期望其中30个首float为1，其余inactive槽为0。

这与dispatch对所有flag float求和的8N / 8N+0.25 / 8N+0.5不是同一公式。inactive槽必须干净，所以Host初始化/跨case清理与设备清flag都是协议的一部分。

晚到的第一个token会卡住其他token吗？

不会固定只等token0。设备维护pending token表，轮询未完成token，谁的回包就绪就先处理谁；完成后把尾项换进当前位置继续扫。输出地址仍按原token编号写，所以完成顺序不改变输出行顺序。

9. 清flag、复用UB、quiet，分别在保护谁？

动作保护的对象不能推导出的结论
读到返回flag满足期望接收端读取这一代消息的前提不能据此释放发送方的全部GM源。
lane的MTE2/V/MTE3事件某一块UB生产/消费之间的先后关系不是所有核、所有rank都完成了。
M4→M5按槽退休输出事件M5可能复用M4还在被读取的UB地址不能在M4返回后直接重置整片arena。
quiet / CQ退休NIC不再需要本批注册GM发送源不等于接收端已经消费或写完最终y。
双bank＋同序调用＋combine_reuse下一代写入不能碰坏当前代仍需读取的数据双bank本身不是任意并发stream或旧handle的通用保护。

M4和M5共享UB布局。M5第一次把某块旧输出区改作输入时，按布局记录的重叠关系等待对应MTE3事件，并通过Vector桥接到MTE2；不是盲目等所有输出，也不是完全不等。最后DrainSharedOutputs回收尚未消费的事件，包含空M4时播种的事件。

M5在本核最后一个待处理token已经就绪、且不再需要任何flag探测时，清本核所负责token的全部K×blocks标志。随后仍可能读取最后token的body；清理不改body，并依赖跨调用复用约束防止新一代提前覆盖。不能把这里改写成“整个数据区清零”。

外层kernel最后先PIPE_ALL，完成本核业务DMA；再借用已经退休的scratch，Flush返回批次的尾CQ。所有原始源/暂存都有明确生命周期，不能因尾片SO就把quiet全部删除。

10. G4、非去重、FP8：放回正确的边界里

场景主线的变化保持不变的理解
EP32/64/128/256当前始终去重，G16；每个异组就是一台16-rank主机。每个非空目标组：1条路由走DIRECT，多条形成FIRST_HOP。
EP16、B_cap>32G4去重，跨逻辑组可能仍在同一物理主机，走MTE。FIRST_HOP/TERMINAL/partial的算法角色仍成立。
EP16、B_cap≤32非去重；不执行TERMINAL stage/组ready/M4。前半核把全部行作为DIRECT返回，后半核M6等完整K路并加权。不能带着旧source_mask的去重解释读M6。
FP8 dispatch＋BF16 combine输入可预量化传输，专家计算后给combine BF16结果。“FP8测试配置”不代表combine收发原生FP8。
公开入口与内部特化分开看

Python公开LL的FP8形态是预量化E4M3FN及配套scale。底层还编译FP16/BF16内部量化等特化；这些不是这份主例的实际执行路径。不要把“源码里存在”写成“默认一定执行”。

11. 用这些问题收尾，确认已经理解代码

  1. 为什么TERMINAL不直接跨机回源？因为它的贡献由同组FIRST_HOP统一读取、加权形成partial。
  2. 为什么source_mask不把k2/k3置1？对应贡献已折入firstK槽，不再有独立回包producer。
  3. 为什么FirstHop原权重存两处时，源端改成1？包尾保留原权重供M4；源端1用于消费已经加权的partial。
  4. 为什么T=0不能直接退出整个combine？本卡仍可能有B个源token要在M5等回包，还要参加本组ready协议。
  5. 为什么M4结束后不等尾CQ也能进入M5？所有put已提交，GM源被外层batch保持；M5仅按重叠关系复用UB，不覆盖在途GM槽。
  6. 为什么不能对比两个不同SDK的结果就说kernel优化生效？SDK会改变实际WQE/队列行为；版本身份、源码和采样条件需要同时记录。

最后请听众自己完成：从rank17的expert_y[row0]出发，依次说出slot410、rank16的M4、源rank0的return槽1、source_weights=1，以及y[t0]。

阅读源码时优先检查的四类错误
  • 地址错位：把row当slot、把firstK当K、把B_cap当B。
  • 数学错位：把TERMINAL当DIRECT、partial再次乘首跳原权重、调整Cast/累加顺序却宣称逐bit不变。
  • 生命周期错位：未完成MTE3读取就覆写UB、put提交后立即重用注册GM、清flag后允许新bank代覆盖body。
  • 参与者错位：空任务核漏通知、把8通知核当8QP/8rank、把dispatch的M/S/R直接套到combine。
